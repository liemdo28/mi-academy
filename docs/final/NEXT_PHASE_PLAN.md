## P2 — production readiness sweep

7a. ~~Postgres + Redis production-like validation~~ — **DONE (fix/full-phase-1-to-19).** Added a `postgres-integration` CI job: real `postgres:16`/`redis:7` service containers, `alembic upgrade head` against actual Postgres (previously never validated -- confirmed locally that SQLite can't even run one of the existing migrations, `ALTER CONSTRAINT`, so this migration chain had never been genuinely exercised end-to-end before), then boots the app under `APP_ENV=production` with a real Postgres/Redis config and polls `/health/live` + `/health/ready` (the latter queries the engine directly). Passed on the first CI run. Closes the "Production Redis connectivity has not been validated against a real deployed environment" gap noted in the Phase 15 report.
7. ~~Security review~~ — **PARTIAL, real gaps fixed (fix/full-phase-1-to-19).** Audited auth/PIN/JWT/PII handling and fixed 3 concretely exploitable gaps: (a) refresh tokens were plain JWTs with no server-side revocation, so `/auth/logout` did nothing and a stolen refresh token stayed valid up to 30 days — now tracked via a `refresh_tokens` table, rotated (single-use) on every `/auth/refresh`, and revoked on logout; (b) the parent PIN (4-6 digits) had no server-side brute-force lockout, only a client-side UI one trivially bypassed by calling the API directly — now locks server-side after 3 wrong attempts; (c) the rate limiter trusted a client-supplied `X-Forwarded-For` unconditionally, letting any caller get a fresh rate-limit bucket per request — now only honored when `TRUST_PROXY_HEADERS` is explicitly set. See `apps/api/dependencies.py`, `apps/api/middleware/rate_limit.py`, 10 new tests. Not done: broader pentest-style review, dependency/CVE triage beyond the existing non-blocking CI scans, deciding whether to make `security-scans` blocking.
8. ~~Performance pass~~ — **PARTIAL, bounded to what's checkable without a device/profiler (fix/full-phase-1-to-19).** No device/emulator is available in this environment, so startup/jank/memory profiling wasn't attempted (documented limitation, not skipped silently). Code-reading audit found and fixed 3 real issues: N+1 queries on `list_lessons`/`get_recommended`/`get_daily_plan` (each accessed `lesson.subject` in a loop with no eager load -- fixed with `selectinload`), missing indexes on `daily_sessions.child_id` and `child_rewards(child_id, unlocked_at)` (every parent dashboard load was scanning unindexed columns), and an unconfigured connection pool (now explicit `DB_POOL_SIZE`/`DB_MAX_OVERFLOW`, Postgres-only since SQLite doesn't support these kwargs). Not done: device-based startup/asset-loading/jank measurement.
